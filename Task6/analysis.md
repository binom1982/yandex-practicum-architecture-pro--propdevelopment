# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

### 1. Доступ к секретам:

- **Кто:** `system:serviceaccount:secure-ops:monitoring`
- **Где:** `namespace: kube-system`, ресурс: `secrets/default-token-xyz`
- **Почему подозрительно:** Сервисный аккаунт `monitoring` не должен иметь прав на чтение секретов в системном неймспейсе `kube-system`. Это может указывать на горизонтальное перемещение или кражу учетных данных.

### 2. Привилегированные поды:

- **Кто:** `admin` (группа `system:masters`)
- **Комментарий:** Создан под `privileged-pod` с `securityContext.privileged: true`. Привилегированные контейнеры имеют полный доступ к хосту, что нарушает принцип минимальных привилегий и может привести к компрометации узла.

### 3. Использование kubectl exec в чужом поде:

- **Кто:** `admin` (группа `system:masters`)
- **Что делал:** Выполнена команда `exec` в поде `coredns-xyz` в неймспейсе `kube-system`. Это позволяет получить интерактивный доступ к системному поду, что может использоваться для скрытного выполнения команд или сбора данных.

### 4. Создание RoleBinding с правами cluster-admin:

- **Кто:** `admin` (группа `system:masters`)
- **К чему привело:** Сервисному аккаунту `monitoring` назначены права `cluster-admin` через `RoleBinding` в неймспейсе `secure-ops`. Это эскалация привилегий: аккаунт с ограниченными правами получил полный доступ ко всему кластеру.

### 5. Удаление audit-policy.yaml:

- **Кто:** `admin` (группа `system:masters`)
- **Возможные последствия:** Удаление или изменение политики аудита отключает логирование критических событий, что скрывает дальнейшие злонамеренные действия и нарушает требования комплаенса.

## Вывод

Выявлена цепочка действий, характерная для атаки на Kubernetes-кластер:

1. Злоумышленник с правами `admin` создал привилегированный под для доступа к хосту.
2. Получил доступ к системному поду через `exec` для разведки.
3. Назначил сервисному аккаунту `monitoring` права `cluster-admin` для закрепления доступа.
4. Удалил политику аудита, чтобы скрыть следы.

**Рекомендации:**

- Ограничить использование `privileged: true` через PodSecurityPolicy / Pod Security Admission.
- Запретить `exec` в системные неймспейсы для некритичных пользователей.
- Включить защиту от изменения/удаления `audit-policy` через RBAC и admission-контроллеры.
- Настроить алерты в SIEM на события: создание привилегированных подов, эскалация прав через RoleBinding, доступ к секретам в `kube-system`.
