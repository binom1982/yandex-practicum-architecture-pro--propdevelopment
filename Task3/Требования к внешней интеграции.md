# Требования к внешней интеграции с платформой партнера «Умный дом».

## Требования к безопасности

1. **Изоляция периметра:** Прямое взаимодействие между мобильным приложением собственника и инфраструктурой партнера  **запрещено**. Все запросы должны проходить через внутренний компонент `smart-home-adapter` в демилитаризованной зоне (DMZ) или выделенном сегменте сети PropDevelopment.
2. **Защита данных (Data Protection):**
   * Биометрические данные (изображения лиц) не должны храниться в базах данных PropDevelopment. Они передаются транзитом напрямую в систему партнера по защищенному каналу.
   * Данные о государственных номерах автомобилей должны передаваться только в хешированном виде или по защищенному каналу, если партнер требует оригинал для сверки.
   * Весь трафик должен быть зашифрован с использованием TLS.
3. **Контроль доступа:**
   * Реализовать строгую проверку прав: пользователь может управлять только теми устройствами (домофон подъезда, шлагбаум двора), которые привязаны к его адресу регистрации в базе `tenant-core-db`.
   * Запрет на массовый перебор устройств (Rate Limiting) на уровне адаптера.
4. **Аудит:** Все действия (открытие двери, добавление лица, открытие шлагбаума) должны логироваться в внутренней системе аудита PropDevelopment с указанием: кто, когда, какое устройство, результат.

## Протоколы аутентификации и авторизации

1. **Аутентификация пользователя (Mobile -> Adapter):**

   * Используется существующий механизм OIDC/OAuth2 через `auth-service-1` (Keycloak). Мобильное приложение передает JWT-токен. Адаптер валидирует токен.
2. **Аутентификация системы (Adapter -> Partner):**

   * Использовать поток  OAuth2 Client Credentials Grant .
   * Система PropDevelopment (`smart-home-adapter`) выступает как конфиденциальный клиент.
   * Обмен токенами доступа должен происходить через защищенное хранилище секретов (например, Kubernetes Secrets или HashiCorp Vault).

## Организация взаимодействия

1. **Архитектурный паттерн:** Anti-Corruption Layer (ACL).
   * Компонент `smart-home-adapter` реализует этот паттерн. Он преобразует внутреннюю модель данных PropDevelopment (ID собственника, ID квартиры) во внешнюю модель партнера (ID резидента, ID устройства доступа) и наоборот. Это защищает ядро системы от изменений в API партнера.
2. **Синхронность и асинхронность:**
   * Команды управления (Открыть дверь, Открыть шлагбаум): Синхронный вызов (REST API) с таймаутом не более 2-3 секунд для обеспечения UX.
   * Статусы и события (Дверь открыта по лицу, Номер распознан): Асинхронное получение через Webhooks от партнера на публичный эндпоинт адаптера (защищенный подписью запроса) или через polling (если Webhooks невозможны), с последующей push-уведомлением пользователю в мобильное приложение.
3. **Обработка ошибок:**
   * При недоступности партнера мобильное приложение должно получать понятное сообщение («Сервис временно недоступен»), а не техническую ошибку.
   * Реализовать механизм повторных попыток (Retry Policy) для критических операций записи (например, регисрация нового лица), но не для операций открытия доступа в реальном времени.
